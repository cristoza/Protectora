# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

"Escudo Visual": a thesis project (UI and API messages are in Spanish) that audits an uploaded image's metadata (EXIF/XMP/IPTC/PNG text) to estimate how exposed it is to AI scraping. It is a monorepo of two independent apps with no root-level tooling (git remote: github.com/cristoza/Protectora): `backend/` (FastAPI, Python 3.9: no `match`, no `X | Y` annotations) and `frontend/` (React 19 + Vite + Tailwind 4, plain JS/JSX, no TypeScript). Backend tests use pytest; the frontend has none.

## Commands

Backend (run from `backend/`; a `.venv` already exists there):
- `source .venv/bin/activate && pip install -r requirements.txt`
- `uvicorn main:app --reload --port 8000`. The port must be 8000 because the Vite proxy targets it.
- `curl http://127.0.0.1:8000/api/health` checks that the backend is up (`live_cloak` says whether `/api/protect` is enabled).
- `python -m pytest -q` runs the tests (`pytest.ini` sets `pythonpath = .`). The `no_leftover_temp` fixture fails if any temp file survives a request.
- Optional accounts need PostgreSQL (local `postgresql@18` via brew): `createdb escudo_visual && createdb escudo_visual_test`. `DATABASE_URL` defaults to `postgresql:///escudo_visual`; `TEST_DATABASE_URL` to `postgresql:///escudo_visual_test` (`tests/test_accounts.py` is skipped if it is unreachable). The schema is created on first connection. Set `COOKIE_SECURE=1` when served over HTTPS.
- `ENABLE_LIVE_CLOAK=1` enables `/api/protect` (otherwise 503 and PyTorch is never imported). `EVAL_EXPORT_TOKEN` enables `/api/evaluations/export` (otherwise 403).
- Scripts run as modules from `backend/`: `python -m scripts.build_corpus <dir>`, `python -m scripts.run_validation`, `python -m scripts.generate_examples` (needs PyTorch and the VAE; writes `frontend/public/examples/`).

Frontend (run from `frontend/`):
- `npm run dev` serves on :5173 and proxies `/api` to `http://127.0.0.1:8000` (see `vite.config.js`)
- `npm run build`
- `npm run lint` (oxlint, config in `.oxlintrc.json`)

## Architecture

- `POST /api/audit` (`backend/main.py`) validates the extension (`ALLOWED_EXT`) and the size (25 MB, `MAX_BYTES`). It writes the upload to a temp file, runs `MetadataReader(path, filename).analyze()`, returns `AuditResult.to_dict()`, and always deletes the temp file in `finally`. That deletion is a deliberate privacy guarantee that the frontend footer advertises, so keep it intact. CORS only allows the localhost:5173 origins.
- `backend/core/metadata_reader.py` holds all the analysis logic:
  - Four readers (`_read_exif`, `_read_xmp`, `_read_iptc`, `_read_text_chunks`) each produce `Finding(source, key, value, category)`. The XMP reader parses with regexes, not an XML parser.
  - `_categorize` assigns a category (`author|copyright|exclusion|privacy|info`) from keyword hints. The score and the `has_*` flags are all derived from these categories.
  - `find_exclusion_tags` scans for AI opt-out directives (`noai`, `noimageai`, `tdm-reservation`, ...) in findings and in the raw XMP.
  - `_score` starts at 100 (fully exposed) and subtracts the `PENALTY_*` constants for protections found. A higher score therefore means MORE vulnerable. `risk_level` is `alto` at 70 or above, `medio` at 35 or above, and `bajo` below that. The frontend consumes the `to_dict()` shape, so changing it means updating `DiagnosticPanel.jsx`.
- `POST /api/stress-test` (`backend/main.py`) takes `file` plus form fields `quality` (1-95), `scale` (0.1-1.0) and `passes` (1-5), runs `core/image_stressor.py` (`ImageStressor`: Lanczos resize, then JPEG recompression with no metadata) and returns `image/jpeg`. It deletes the temp file in `finally` like `/api/audit`. Validation errors from FastAPI come back as a `detail` list, not a string.
- `POST /api/stress-suite` runs `core/resistance_suite.py` (`run_suite`): JPEG 50/75, resample, crop, format change and a simulated screenshot, each row reporting `metadata`, `c2pa`, `noai` and `watermark` as `sobrevive|no sobrevive|no aplica`. It copies EXIF/XMP/ICC when re-encoding (best case). The watermark is drawn by the suite with `core/watermark.py` (torch-free; `image_protector` reuses it) and detected by Pearson correlation of high-passed luminance against a signed mask, threshold `WATERMARK_THRESHOLD = 0.10`, with a no-mark negative control per row. Intermediates live in a `mkdtemp` folder removed in `finally`.
- `POST /api/publication-advice` audits the upload and evaluates `core/publication_rules.json` (`core/publication_advisor.py`) over the `to_dict()` report plus `lossy` and an estimated `jpeg_quality`. Edit rules in the JSON, not in code.
- `POST /api/evaluations` stores anonymous SUS + comprehension answers in `backend/data/evaluations.sqlite` (gitignored; Pydantic models forbid extra fields). `core/sus.py` implements Brooke (1996).
- Knowledge tests (`core/knowledge.py`): `GET /api/knowledge/{diagnostico|final}` serves the ADDIE instruments from `docs/addie/instrumentos/` (read on every request) without `correct`/`feedback`; `POST` validates every answer against the instrument, grades on the server, stores one row per code and phase in table `knowledge_tests` of the same SQLite (409 on repeat) and returns `by_objective`; only `final` adds per-item `results` and, when a diagnostic exists for the code, `comparison` with Hake's normalized gain. `GET /api/knowledge/export` uses the same `EVAL_EXPORT_TOKEN`. Bump an instrument's `version` when changing it after use; `validated: false` makes the UI show a test-version notice. The anonymous code lives in `sessionStorage` (`lib/participant.js`) and is shared by `KnowledgeTest` (entry cards in the map and summary steps, `aside` in `App.jsx`) and `EvaluationFlow`.
- `POST /api/protect` (`backend/main.py`, disabled unless `ENABLE_LIVE_CLOAK=1`, lazy-imports `ImageProtector`) takes `file` plus form fields `strength` (`baja|media|alta`), `watermark_text` and `watermark_opacity` (5-90). It runs `core/image_protector.py` (`ImageProtector.compare`) in a threadpool and deletes the temp file in `finally`. The Glaze-like cloak is a PGD attack (L-inf epsilon 4/8/16, 30 steps) on the Stable Diffusion VAE encoder (`stabilityai/sd-vae-ft-mse`, downloaded to the Hugging Face cache on first use, run on MPS when available) toward a fixed pattern, computed at 512 px and upsampled onto the image (capped at 2048 px). It is compared with a tiled visible watermark using the same metrics: SSIM for a person (protected vs original) and SSIM for the model (VAE reconstruction of protected vs of original), also after JPEG 75. It returns base64 data URLs (PNG for downloads). A module-level lock serializes model use, and a request takes about 25-60 s.
- `POST /api/write-metadata` (`backend/main.py`) takes `file` plus form fields `author` (required), `copyright` (defaults to `© <year> <author>`), `ai_opt_out` and `strip_gps`. `core/metadata_writer.py` writes EXIF Artist/Copyright and replaces the XMP packet with `dc:creator`, `dc:rights`, `xmpRights` and, when opting out, `noai`/`noimageai` keywords, IPTC `plus:DataMining` (`DMI-PROHIBITED-AIMLTRAINING`) and TDMRep `tdm:reservation`. Pixels never change: JPEG only has its APP1 segments rewritten (no re-encode), PNG/TIFF are lossless and WebP is saved `lossless=True`, so a cloak survives signing. It audits the written file with `MetadataReader` and returns `{filename, image (data URL), audit}`, deleting both temp files in `finally`. `EXCLUSION_PATTERN` in the reader must keep matching everything the writer emits.
- Accounts (optional, `core/db.py` + `core/accounts.py`, plain SQL with psycopg 3, no ORM): username + password (PBKDF2-SHA256 from the stdlib; `hashlib.scrypt` is missing in the macOS 3.9 build), session token in the httpOnly cookie `ev_session` with only its SHA-256 stored (30 days). Endpoints: `/api/auth/register|login|logout|me` (`DELETE /api/auth/me` deletes the account, its rows by cascade and its upload folder), `GET/PUT /api/progress` (the Aprendizaje state from `App.jsx`, Pydantic `extra="forbid"`, including `protection` and `stress` settings), `GET/POST /api/projects`, `GET/PATCH/DELETE /api/projects/{id}` (named Laboratorio projects whose state is `LabState`: identity, protection, stress, audit; deleting one deletes its images and files), `GET/POST /api/images` (optional form field `project_id`), `GET /api/images/{id}/file`, `DELETE /api/images/{id}`. Saved images live in `backend/data/uploads/<user_id>/` with their path and audit in Postgres; `section` is `aprendizaje|laboratorio`, `kind` is `original|firmada|perturbacion|marca_agua`. Every query filters by `user_id`. Nothing is stored unless the user presses "Guardar en mi cuenta"; the anonymous endpoints keep deleting their temp files. A `psycopg.OperationalError` becomes a 503 so the rest of the app works without Postgres. Evaluations stay anonymous in SQLite.
- C2PA: `read_c2pa()` in `metadata_reader.py` fills `to_dict()["c2pa"]` (`present`, `valid`, `issuer`, `generator`, `ai_generated`, `errors`). It does not affect the score. `c2pa-python` is pinned `<0.9` because 0.9+ needs Python 3.10 and the venv is 3.9; the 0.8 API needs a hand-written `Stream` adapter (`_FileStream`).
- Frontend sections: the header toggles **Aprendizaje** (the guided flow below) and **Laboratorio** (`components/LabView.jsx`: the same tools without steps, with their own state, plus `MyImages`). `lib/account.js` holds `AccountContext` (user, `imagesChanged`), `SectionContext` (which section a saved image belongs to) and the API helpers. `AccountMenu` is a native `<dialog>` for login/register/logout/delete. `SaveImageButton` renders only with a session and is placed next to the upload (layer 1 and lab), the signed result in `MetadataSigner`, and the live `ProtectionLab` cards (not the precomputed example). With a session `App.jsx` restores the saved Aprendizaje progress on login and saves it with a 1 s debounce. A third header section, **Proyectos** (`components/ProjectsView.jsx`), lists Laboratorio projects grouped by date (creation or last change, search, order), with a detail view (settings, images) and create/open/rename/delete. Lab state lives in `App.jsx` through `lib/useLabProject.js`, so it survives section changes; the open project (`project` in `AccountContext`) is autosaved with a 1 s debounce, receives the lab upload automatically and the lab images saved with `SaveImageButton`; opening one restores its settings plus its latest `original` image. Without an open project nothing from the lab is saved. `ProtectionLab` and `StressSimulator` take their settings as props (`protection`, `settings`).
- Frontend (`frontend/src`) is a guided, step-by-step flow over four protection "layers" (metadata authorship, AI-exclusion tags, visual perturbation, publishing), preceded by a map step and a "Conceptos clave" literacy step (`data/literacy.js`, Module 1) and followed by a summary step. `EvaluationFlow` (consent, SUS from `data/evaluation.js`, `data/comprehension.json`) is a separate view toggled from the summary and the footer.
  - `data/addie.js` summarizes the ADDIE instructional design in `docs/addie/` (objectives with their steps and evaluation codes, phases with done/pending, evaluation dimensions, rigor rules). `StepObjectives` shows a collapsible "Qué aprenderás en este paso" in `StepFrame`, the map and the summary; `PedagogyView` is a read-only view opened from the footer and the summary (`aside` in `App.jsx`, like `EvaluationFlow`), never a new step. Keep it in sync with `docs/addie/02_diseno.md` and do not present pending items as validated.
  - `data/layers.js` is the single source of truth: step order, each layer's "viene de / lleva a" text, and `getStatus()`, which derives each layer's `done|missing|pending` state. Add or reorder steps there and reference steps with `stepById(id)`, never by index.
  - `App.jsx` owns all shared state (`index`, `audit`, `perturbed`, `checks`), renders the matching view from `components/steps/`, and moves focus to `#step-title` on each step change. `LayerRail` is the always-visible clickable map (a horizontal stepper in the sticky header), so users can jump back to any layer.
  - Layers 1 and 2 are verified against real data (the `/api/audit` or `/api/write-metadata` audit). Layer 3 is `done` when a cloak was generated in `ProtectionLab` (`cloaked`, only possible with the live cloak) or the user ticks the checkbox for an external tool. Layer 4 shows the `/api/publication-advice` recommendations for the current file (`current` in `App.jsx`: the upload or its latest signed version, via `usePublicationAdvice`) and is `done` when every recommendation is ticked; ticks are user-declared, so do not present them as verified.
  - `MetadataSigner` calls `/api/write-metadata`. It appears in layer 1 (signing the uploaded `source` file) and under the `ProtectionLab` results (signing the cloak PNG). Signing updates the app-wide `audit` to the signed file. The signing form values (`identity`) live in `App.jsx` and are shared by both places.
  - `AuditDropzone` posts a `FormData` field named `file` to a relative `/api/audit` URL, so it only works through the Vite proxy (or a same-origin deploy). The backend's `detail` string is shown as the error message, so backend error text is user-facing. `DiagnosticPanel` renders the `to_dict()` result.
  - `ProtectionLab` (inside the layer 3 step) checks `/api/health`; without `live_cloak` it renders the precomputed `/examples/manifest.json` (same shape as `/api/protect`) and hides upload and signing. With it, it calls `/api/protect` on button press, with abort. It shows SSIM rings per technique (the one with lower model similarity gets a badge), a drag slider comparing the original with the cloak or watermark in person or model view, and both difference images. The watermark overlay on the preview is a CSS approximation; the real one is drawn by the backend. It is real output, but layer 3 stays user-declared.
  - `StressSimulator` (inside the layer 3 step) calls `/api/stress-test` with debounce and abort on every slider change. `ResistanceTable` (also layer 3) calls `/api/stress-suite`. `CompareSlider` (literacy step) only uses the local precomputed files in `public/examples/`; the UI must not make network calls.
  - Styling: Tailwind v4 with CSS-variable tokens in `index.css` (`bg-bg`, `text-muted`, `bg-accent`, `accent-2`, `highlight`, ...). The theme is light-only by design (no dark mode). Shared component classes live there too (`.card`, `.hero-panel`, `.btn-*`, `.marker`, `.spotlight`). Use these tokens instead of raw palette colors. Fonts are Geist via `@fontsource-variable`, icons are Phosphor, and motion uses `motion/react` with shared easing/stagger helpers in `src/lib/motion.js` (honor `useReducedMotion`). UI copy is Spanish and avoids em-dashes.
- Both servers must be running for uploads to work. A `Failed to fetch` message in the UI, or `ECONNREFUSED 127.0.0.1:8000` in the Vite log, means the backend is down.
